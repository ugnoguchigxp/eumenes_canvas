# 保存・復元の設計書

2026年11月12日。独立版で、保存・復元の成功を返した版が再起動後も開けるようにする。同時操作、取消、再試行を含めて、利用者に返した結果と保存版の履歴を一致させる。 [改善計画書の01・02](improvement-plan.md#2-最優先の修正)

## 対象と責務

独立版の `CanvasService` が候補の採用条件、所有者、版、受領キーを照合し、`Store` が版と受領結果を一つの更新として確定する。既存の `store.json` 形式、公開API、作品のハッシュ計算を使う。独立版は単一プロセスの単一書き込み元を前提とする。本体取込時は、Eumenes の既存の保存・版管理で同じ契約を検証する。 [独立版と本体の責務](../design.md#2-独立側と-eumenes-の責務)

## 保存と復元の確定順序

1. 受領キーを検査し、確定済みの同一要求には前回の結果を返す。キーが一致しても要求内容が異なる場合は競合として扱う。
2. 採用候補または復元元を読み、本文のハッシュを照合する。
3. ハッシュ照合後、書き込み順が来た時点で確定済みの受領キー、所有者、現在版を照合する。保存では候補を採用できる実行状態か、検証済みの候補と本文が一致するかも照合する。次の書き込みは、この操作が確定するか失敗するまで待つ。
4. 新しい版、作品の現在版、受領結果をまとめて確定する。確定後にのみ成功を返す。競合した場合は候補と既存の履歴を残し、現行のエラーコードを返す。

同じ現在版からの異なる要求は、最初に確定した操作だけが成功する。同じ受領キー・同じ要求が重なった場合は、その成功を両方に返す。取消・撤回が先に確定していれば候補は採用できない。保存が先に確定した場合、その版は履歴に残る。

画面は受領結果から保存・復元を表示し、一覧・履歴の取得結果をそれぞれ表示する。受領結果を確認できなかったときは、同じ画面から同じ操作をやり直すと受領キーを再利用する。再取得した受領結果には操作を確定した時点の版が入るため、画面が既に知っている新しい現在版は保つ。復元の受領結果があれば、一覧と履歴を取得できなくても確定した版をプレビューできる。「作品情報を再取得」は現在の一覧・履歴を読み直す。

## 永続化に失敗した場合

ストアは確定済みの状態から次の状態を作り、既存の一時ファイルと置換処理で保存する。書き込みの完了を待つ間も一覧やプレビューを返せる。置換が成功したあとで、画面・次の操作が読む状態を切り替える。書き込みや置換が失敗した場合は、最後に確定した状態を読み続け、失敗した操作の受領結果は返さない。

更新処理は、書き換える記録の種類を宣言する。ストアはその記録だけを複製して作業用の状態を作り、`store.json` 全体を従来の形式で置き換える。制作の途中経過は実行記録だけを更新する。検査結果からその場で提示できる候補が決まった場合は、候補・検査・提示状態を一つの置換で確定する。別の試行や再生結果との比較が必要な場合は、既存の候補選択の流れを使う。

確定した保存版と候補は読み取り専用にし、作業用の表では追記または置き換えを行う。変わっていない表のUTF-8バイト列を再利用し、一つのJSONとして一時ファイルに書く。部分書き込みの場合は残りを続け、ファイルを閉じてから置き換える。プレビューと実行の問い合わせで返す作品・検査の詳細は呼び出し側で変更できるコピーにする。

生成の進行・取消など、同じストアを使う操作も書き込み順が来た時点で状態を照合する。取消と撤回は対応する状態を確定してから実行を中断する。期限を過ぎた制作はその場で中断し、期限切れの記録を順番に確定する。ファイルを使わない試験でも、更新処理が途中で失敗した場合は最後に確定した状態を参照する。

実行の途中で状態を保存できなくなった場合は、生成・観測を中断する。失敗状態を保存できる間は台帳に記録し、保存先が復旧していない間は、台帳に残った「実行中」とホストの実行中一覧を照合して問い合わせ時に中断を表示する。期限の時点では停止を優先し、期限切れの記録に失敗しても処理を打ち切る。復旧後は通常どおり新しい依頼を受け付ける。

更新ごとに次の状態を作るコストが加わるため、作品と履歴を含む代表的な保存先で時間を確認する。現在の構成では一つのファイルに版と受領結果を含められ、既存データをそのまま読める。電源断や複数プロセスによる同時書き込みの保証は、運用要件が生じた段階で別途検証する。

## 検証

| 順序 | 確認すること | 期待結果 |
| --- | --- | --- |
| 部分 | 同じ受領キーの重複、異なる操作による同一キー使用、同じ現在版からの保存・復元、ハッシュ照合中の取消・撤回 | 重複は同じ結果。異なる要求の競合では版が一つだけ進み、取消・撤回が先なら候補を保存しない。 |
| 部分 | 試験用の保存先で一時ファイルへの書き込みと置換を失敗させる。障害除去後、同じキーで再試行する。 | 失敗直後は旧版を開け、成功した再試行で初めて新版が見える。新しいストアで開いても版、本文、受領結果が一致する。 |
| 部分 | 生成中または期限到達時に一時ファイルへの書き込みを失敗させる。 | 処理が終了して問い合わせに失敗状態が返る。候補と保存版は作られず、復旧後の依頼が完了する。 |
| 結合 | 保存・復元APIを使う既存の結合試験と、旧形式のストアを開く試験 | 既存のレスポンスと競合コードで処理し、旧保存版の本文と履歴を参照できる。 |
| 通し | `bun run verify` で既定のブラウザを使い、制作から保存・復元、停止と再起動まで確認 | 型検査、部分・結合、対象ブラウザの試験が通る。スキップと残る制約を記録する。 |

macOS arm64、Bun 1.4.4で、本文約16 KiBの合成履歴を使い、ファイルへの更新を各条件12回測った。約16 MB（1000版）のとき、更新のP90は変更前21.15ms、変更後21.81ms。更新単体の測定で、複数タブの待ち時間と長時間負荷は改善計画の10で扱う。

## 履歴がある状態での画面操作

macOS arm64、Bun 1.4.4、Playwright 1.65.0のChromiumで、`bun scripts/measure-local-workload.ts 1000` を実行した。1作品10版、本文約16 KiB、候補・検査記録を含む合計約34.8 MBの合成履歴を使った。1回予備起動したあと、固定応答で制作・プレビュー・保存を5画面同時に4組実行した。各版・各条件で20件を測り、すべて提示・保存できた。`10` を指定すると、小さい履歴で比較できる。

| P90 | 1回目の変更前 → 変更後 | 2回目 | 3回目 |
| --- | ---: | ---: | ---: |
| 依頼入力開始から候補表示 | 4.660 → 4.083秒 | 4.541 → 3.822秒 | 4.577 → 4.045秒 |
| 候補表示からプレビュー起動 | 156 → 82 ms | 337 → 180 ms | 165 → 81 ms |
| プレビュー起動から画面の保存完了 | 385 → 285 ms | 424 → 482 ms | 370 → 469 ms |
| ホストの20 ms間隔の処理が遅れた時間 | 57.7 → 17.5 ms | 55.7 → 29.0 ms | 27.3 → 8.7 ms |

第3回のサーバー内の保存処理はP90が156.9 → 146.4 ms。画面で保存完了を確認するまでの時間は比較ごとに増減した。候補表示までの時間は3回とも12〜16%短縮した。履歴10版の初回比較では、候補表示のP90は2.940 → 2.885秒、画面の保存完了は110 → 122 msだった。

ホストの実メモリ使用量は、1000版の3回で最大205〜476 MiBから349〜429 MiBの範囲に変動した。Chromiumの別プロセスはこの値に含まれない。同期書き込みが重なったときは処理の遅れが最大508 msあり、長時間利用でのメモリと最大待ち時間は引き続き測る。実モデルの時間・費用はこの計測の範囲外。

## 150件の連続利用と書き込み待ち

`bun scripts/measure-local-workload.ts 1000 30` で、1000版から始めて5画面ずつ30組、各条件150件を制作・プレビュー・保存した。各回は約130〜132秒で全件保存した。書き込み中も最後の確定状態を返す方式に変更し、期限と書き込み順の回帰を修正する前後に計2回測り直した。

| 指標 | 変更前 | 変更後1回目 | 変更後2回目 |
| --- | ---: | ---: | ---: |
| 一覧取得 P90／最大 | 13.4／742.4 ms | 10.0／92.4 ms | 10.4／105.5 ms |
| ホストの処理遅れ P90／最大 | 21.8／508.3 ms | 46.1／101.6 ms | 45.7／108.6 ms |
| 候補表示 P90 | 4.065秒 | 4.036秒 | 3.984秒 |
| 画面の保存完了 P90／最大 | 449／505 ms | 450／967 ms | 542／1084 ms |
| サーバーの保存処理 P90 | 198 ms | 297 ms | 307 ms |
| ホストの実メモリ P90／最大 | 107／253 MiB | 105／432 MiB | 101／415 MiB |

最大の一覧待ちとホストの処理遅れは、2回とも短くなった。保存の応答には書き込み順を待つ時間も含まれ、画面上の保存完了が遅い例は増えた。保存形式は従来のJSONで、更新ごとに全体を書き出す。メモリの最大値は増えたが、変更後2回目の各5組終了時点で、観測用と画面用のChromiumを含む子プロセスのRSS合計は1,390〜1,438 MiBの範囲だった。RSS合計は共有ページを重ねて数える場合がある。計測は固定応答を使った約2分の負荷で、時間単位の連続利用と実モデルの計測は残る。

履歴10版・4組の比較では、候補表示P90は2.941 → 2.905秒、一覧取得P90は8.3 → 7.1 msだった。候補表示の受入条件とは別に、今後の保存性能の比較では書き込み待ちの時間とメモリの最大値を確認する。

### 保存版と候補の変換結果を再利用した比較

同じ1000版・150件の条件で、版と候補の複製を減らし、変わっていない表のUTF-8バイト列を再利用した。各回とも全件を保存した。固定応答の画面操作全体は132.2秒から103.1秒、103.8秒になった。

| 指標 | 前回の最終計測 | 変更後1回目 | 変更後2回目 |
| --- | ---: | ---: | ---: |
| 画面の保存完了 P90／最大 | 542／1084 ms | 259／337 ms | 254／354 ms |
| サーバーの保存処理 P90 | 307 ms | 137 ms | 138 ms |
| 候補表示 P90 | 3.984秒 | 3.343秒 | 3.330秒 |
| 一覧取得 P90／最大 | 10.4／105.5 ms | 7.5／64.9 ms | 7.9／111.1 ms |
| ホストの実メモリ P90／最大 | 101／415 MiB | 200／313 MiB | 199／526 MiB |

保存完了のP90と最大値は2回とも短くなった。ホストのメモリ使用量のP90は増え、最大値の改善は再現しなかった。変換結果を保持するため、履歴が増えたときの使用量は引き続き測る。書き込みとファイル置換の失敗後の再試行、古い版からの再起動、プレビューの返却データを変更しても保存済みの本文が変わらないことを回帰試験で確認した。
