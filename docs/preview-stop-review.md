# Canvas 作品の実行と停止のレビュー

## 確認した経路

- 制作担当の出力は `CanvasService` が契約検査とブラウザ観測に渡す。契約は構文と利用できる機能を検査し、観測は決まった時刻と入力で描画・例外を確かめる。起動後に特定の状態で起こるループも、保存済みの作品を開くときも同じ実行制限が必要になる。
- Worker とページ直接モードは、共通のプレビューサーバーで保存済みの本文と同梱ライブラリを組み立てて配信する。これまではどちらも作品の同期処理に実時間の上限がなかった。
- シェルは Worker に `terminate()` を要求するか、ページの iframe を外す。以前の実測では、Chromium の Worker 終了に 2,037–2,038ms かかった。ページでは停止応答のあともレンダラーが CPU を消費し、同じプレビューで次の作品を起動できなかった。 [取り込み前の実測](pre-integration-results.md)
- ホストで新しい起動が前の起動待ちを置き換えた場合、前のタイマーが新しい待ちを消す可能性があった。停止した起動の待ちは停止結果で解決する。

## 採用した修正

制作指示に、ループの終了条件、再試行の上限、次のフレームやイベントへの状態の引き継ぎを明記した。配信時に JavaScript の構文木を読み、`for`、`for...of`、`for...in`、`while`、`do...while` のループ本体に検査を挿入する。保存された本文、digest、同梱ライブラリ、CSP は既存の経路を使う。 [TypeScript Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)

同じタスクで最初のループから実時間 750ms を超えてループ本体に入ると、元の行と列を添えて例外を返す。時計はブラウザ観測が仮想時計に切り替える前に確保する。ホストの Worker 終了要求と iframe の取り外しも引き続き行う。ブラウザ API 内で JavaScript に制御が戻らない処理まで強制終了するには、実行プロセスを外側から管理する方式が必要になる。

## 実ブラウザでの停止

macOS のデスクトップ Chrome 157 を Playwright から開いて測定した。停止から Worker 終了まで、描画コールバック内のループは 122ms、最上位のループは 137ms。両方で 2 秒以内に次の作品が起動した。ページ直接モードは次の作品の起動まで 395ms。停止前に CPU を使っていたレンダラーについて、再起動後に CPU 消費が続かないことも確認した。

`bun run verify` は型検査、部分・結合 238 件、ブラウザ 173 件が通過した。ブラウザの既定のスキップは 23 件。Worker の起動時のループと、ページの仮想時計を止めているときのループは、停止ボタンを押す前に元の行と列を添えたエラーを返した。

```sh
CANVAS_DESKTOP_CHROME=1 bun run test:e2e -- tests/e2e/p0-threats.spec.ts tests/e2e/page-mode.spec.ts --grep '無限ループ' --project=chromium --workers=1
```
