# P2 評価の凍結記録

この文書は、制作の記録（eval/recordings）を作る**前**に凍結した評価の条件を記す。凍結した commit より後に、課題・元作品・判定コード・実行器を変えた実行は、本評価の合格数に入れない。

## 体制（正直な表示）

- 利用者の Luna／Haiku はローカル環境のモデルで、この環境からは呼べない。そこで **Grok Bot が制作担当を代行**し、出力を記録済み推論（`RecordedProvider`）として保存して、製品と同じ経路（契約検査 → ホスト観測 → 修正最大 2 回 → 保存）で再生する。
- **評価担当（課題・判定コードの作成）も同じ Grok Bot**。生成と判定は独立していない（盲検ではない）。
- 3 回の試行は新しいセッションの独立した推論ではなく、同じエージェントが 1 回の作業で書き分けた 3 案（sample 0〜2）。
- したがって合格率は「この制作経路と判定の組み合わせで記録済みの案が通るか」を示すもので、Luna／Haiku の性能は**未測定**。
- 遅延は記録の再生（観測・保存を含む）だけを測る。実モデルの推論時間は**未測定**。

## 凍結したもの

| 種類 | 場所 |
| --- | --- |
| 未使用課題 13 件（新規 4・部分修正 4・修復 4・非ゲーム 1） | `eval/tasks/heldout.json` |
| 元作品・不具合入り元作品 | `eval/bases/` |
| 合成データ（3 系列×25 点） | `eval/data/synthetic-sensors.json` |
| 判定コード（画素だけで判定） | `eval/checks/heldout.ts`, `eval/lib/env.ts` |
| 実行器・対照 | `eval/runner.ts` |
| 対照の結果 | `docs/eval/p2-self-test.json` |

調整用の課題は P1 の固定記録（落ち物・ブロック崩し・棒グラフ）で、未使用課題とは元作品と変更内容が重ならない。

## 制作担当に渡すもの

依頼文、基準作品（部分修正・修復）、公開契約 `docs/artwork-contract-v1.md`、登録データの説明、ホスト観測の結果（host-smoke/1）だけ。判定コード・期待値・対照の結果は渡さない（ただし同じエージェントなので、上記の通り実際には見えている）。

## 合格の定義

- 1 試行 = 1 課題の全ターンを通し、各ターンで候補が提示され保存されること。保存された最終版に、その課題の判定（`change`・`retain`・`start`）が**すべて**合格すること。
- 上限：ターンごとに初回 1 回＋修正 2 回、全ターンで推論 6 回以内。超過・未提示・例外は不合格。
- 判定は 1 観点ずつ新しいブラウザ文脈で起動し、手動時計（`advance`）と固定の乱数 seed で動かす。Chromium のみ。

## 対照（凍結前に確認）

| 課題群 | 対照 | 期待 | 結果 |
| --- | --- | --- | --- |
| 新規 | 黒一色の作品 | 全判定が不合格 | 4/4 期待どおり |
| 部分修正・非ゲーム | 元作品 | 変更の判定が 1 つ以上不合格、維持の判定はすべて合格 | 5/5 期待どおり |
| 修復 | 不具合入り元作品 | 同上 | 4/4 期待どおり |
| 修復 | 不具合のない元作品 | 全判定が合格 | 4/4 期待どおり |

制約：新規課題の判定には「合格すべき作品」による対照がない（参照実装を作ると制作担当と同じエージェントが答えを持つため作らなかった）。新規課題で判定側の誤りによる不合格があり得る。評価後に判定を直した場合は別の評価版として扱い、本評価の合格数に混ぜない。

## 実行方法

```sh
bun eval/runner.ts --self-test   # 対照
bun eval/runner.ts --run         # 13 課題 × 3 試行
```
