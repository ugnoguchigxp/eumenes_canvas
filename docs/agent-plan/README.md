# Canvas アプリを作りやすくする計画（制作担当・検証担当・描画の制約）

2026-11-10 作成。実装する人（Grok）に向けた設計書。この README を最初に読み、番号順に 1 冊ずつ実装する。

- 既存の設計は [design.md](../../design.md)、既存の計画は [plan.md](../../plan.md)。この計画はそれらを変えない範囲で足す。変える箇所は各冊に書いてある。
- この計画の対象は、現在のブランチ `main`（commit `2ef97d6`）のコード。

## 1. 何を作るか

いまの制作の流れは「制作担当が 1 回で作品を書く → 契約の検査 → ホスト観測（起動する・エラーが無い・単色でない・どこかで描画が変わる）→ 提示」。依頼どおりに動くかは誰も確かめていない。この計画で次の 3 つを足す。

1. **ホストが確かめることを増やす（推論を使わない）。** エラーの位置、入力ごとの効果、時間を進めない描き直しでの変化、再現性、リサイズ、長時間。
2. **担当を 2 人にする。** 制作担当（Maker）は作品と一緒に「要件と操作の宣言」を返す。検証担当（Evaluator）は別の推論で、ホストが実際に動かして測った結果を証拠に、要件ごとに判定する。指摘があれば制作担当に 1 回直させる。
3. **描画の制約を外す。** 画面の canvas に直接 WebGL で描けるようにし、毎フレームの複写をなくす。更新と描画を分けて、観測中の描画を減らす。後処理のアドオン・ホイール入力を足す。

```
利用者の依頼
   │
   ▼
┌──────────────┐  作品＋宣言（要件・操作）   ┌───────────────────────────┐
│ 制作担当 Maker │ ─────────────────────────▶ │ ホスト                      │
└──────────────┘                             │ 1 契約の検査（必須）         │
   ▲  指摘（要修正・注意）                    │ 2 ホスト観測 host-smoke（必須）│
   │  ※重い指摘があり、試行が残るときだけ      │ 3 性質の観測 host-probe（助言）│
   │                                         │ 4 台本の実行（助言）          │
   │        台本（何を入力し、何を測るか）      │                             │
   │      ┌────────────────────────────────  │                             │
   │      ▼                                  │                             │
┌────────────────┐   観測・測定（証拠 id つき） │                             │
│ 検証担当 Evaluator│ ◀──────────────────────── │                             │
└────────────────┘ ─── 要件ごとの判定・指摘 ──▶ │ 5 最も良い候補を提示         │
                                             └───────────────────────────┘
```

## 2. 変えてはいけない規則

実装中に迷ったら、ここに戻る。

1. **保存の必須条件は変えない。** 保存に要るのは、契約・起動・操作（`contract`・`loaded`・`operated`）の合格だけ。性質の観測と検証担当の判定は**助言**で、保存を止めない（P3 では観測器の偽陰性だけで正しい候補が 10 件落ちた）。
2. **既定の動作は変えない。** 設定で検証を有効にしない限り、今と同じ結果になること。既存の単体試験・Playwright の試験は、各冊で「変える」と書いたもの以外、すべてそのまま通ること。
3. **題材ごとの分岐を書かない。** 依頼の語句（「テトリス」など）で処理を分けない。観測・判定の規則は、どの作品にも同じものを当てる。
4. **観測の固定点の座標を外に出さない。** `src/core/observer.ts` の固定点（クリックの格子）の座標・個数を、制作担当・検証担当に渡す文、契約、手順のどこにも書かない。作品が描いた領域から選んだ点の座標は書いてよい。
5. **評価の資材を製品に混ぜない。** `eval/gold/`・`eval/checks/`・`eval/tasks/` の中身を、`src/`・`docs/maker-*.md`・`docs/evaluator-skill.md` に写さない。`src/` から `eval/` を import しない。
6. **凍結した記録を変えない。** `docs/eval/` の JSON、`docs/p*-results.md`、`docs/general-v1-results.md`、`eval/checks/*.ts`、`eval/gold/`、`eval/tasks/*.json`、`eval/recordings/` は読むだけ。
7. **隔離を弱めない。** 作品 Worker の CSP（`default-src 'none'`）、iframe の sandbox、プレビューの別オリジン、メッセージの型と上限の検査は変えない。足すメッセージは、この計画に書いた型と上限で検査する。
8. **モデルの出力を信頼しない。** 制作担当の宣言、検証担当の台本と判定は、必ず正規化（形の違う部分を捨てる・上限で切る）してから使う。
9. **サーバーを勝手に起動しない。** 検証ホスト（`bun run dev`）の起動・再起動は利用者が行う。試験の中で一時的に立てる待ち受け（既存の試験と同じ形）はよい。
10. **commit・push は頼まれたときだけ。**

## 4. 各冊の読み方

どの冊も同じ並びで書いてある。

1. **目的**：何のために作るか。
2. **触るファイル**：新しく作るファイル、変えるファイル、触ってはいけないファイル。
3. **仕様**：型、定数、規則、文面。ここに書いた名前・数値・文面は、そのまま使う（試験が文面を照合する）。
4. **手順**：上から順に行う。既存のコードを変えるところは、目印になる既存の行を引用してある（行番号は変わるので、文字列で探す）。
5. **試験**：足す試験の名前と期待値。
6. **完了の確認**：打つコマンドと、期待する結果。
7. **間違えやすい点**。

コードの書き方は既存のファイルに合わせる（TypeScript は `strict`、コメントは日本語、2 スペース、行末にセミコロン）。`src/preview/bootstrap.js` と `src/preview/shell.js` はブラウザでそのまま動くので、`var`・`function` を使う既存の書き方を保つ。

## 5. 確認のコマンド

実装の途中は、触った範囲の試験だけを動かす。全体は冊の最後に 1 回。

| 目的 | コマンド |
| --- | --- |
| 型検査 | `bun run typecheck` |
| 単体試験 1 ファイル | `bun test tests/unit/<名前>.test.ts` |
| ブラウザ試験 1 ファイル（Chromium） | `bunx playwright test tests/e2e/<名前>.spec.ts --project=chromium` |
| 全体（冊の最後） | `bun run verify` |

`bun run verify` が通らないまま次の冊へ進まない。通らないときは、実装を試験に合わせて直す。試験の期待値を弱める・消すのは、冊に「変える」と書いてある場合だけ。

## 6. この設計の裏取り

推測で書いた部分と、確かめた部分を分けておく。

**リポジトリの外に写しを作り、試作して確かめたもの（リポジトリのコードは変えていない）:**

- 01 のブートストラップの変更と行番号の計算。偽の Worker 環境（`self`・`OffscreenCanvas` を偽物にする）で、起動・時間の経過・入力・時間を進めない描き直し・更新と描画の分離・直接描画の分岐・エラーの位置が、この設計どおりに動く。
- 02 の画素の道具（差分、画面の要約、色のまとまり）。合成した画像で、要素の色と外接矩形が画素単位で一致する。
- 03 の指摘の規則と文、06・07 の正規化（宣言・台本・判定）、行単位の差分、07 のまとめ役、08 の制作のループ。偽の担当で、この設計に書いた試験の期待値どおりになる。既存の `tests/unit/service.test.ts`・`single-user.test.ts`・`recorded.test.ts` は、08 の変更後もそのまま通る。
- 05 の後処理アドオンの同梱。1 つの束（Three.js の本体は 1 つ）に入り、大きさは 755,502 → 774,505 バイト。
- 構文エラーの位置は `Bun.Transpiler` の `position.line`・`lineText` で取れる（Bun 1.4.4）。

**ブラウザで動かして確かめていないもの（実装の中で、各冊の試験で確かめる）:**

- 02 のハーネスの操作のまとめ、03 の観測の実行部分、07 の台本の実行。既存の `src/core/observer.ts` と `eval/lib/env.ts` と同じ操作の組み合わせだが、実際のブラウザでは動かしていない。
- 05 のシェル側（面を 2 枚重ねる、画面の canvas を Worker に渡す）。WebKit では表示に反映されない場合があった（design.md §4）ので、Chromium だけで有効にする設計にしてある。
- 01 の実行時エラーの行番号が、WebKit のスタックの形でも取れるか。取れなければ位置を付けないだけで、ほかの動作は変わらない。

**外部の根拠（調査で確かめたこと）:**

## 7. 利用者に決めてもらうこと

実装を止める必要は無いが、決まると先へ進めるもの。

1. **実モデルの接続先**（09）。OpenAI 互換の HTTP で呼べるか、別の呼び方か。決まるまでは、既存のファイル応答（代行の応答者）で測る。
2. **検証担当に使うモデル**（09）。制作担当と同じでよいか、別にするか。
3. **ページ直接モードで残る危険を受け入れるか**（10）。DOM・音・素の Web の書き方を使えるようにすると、WebRTC による外向きの通信と、WebKit での無限ループの停止が、今の方式では防げなくなる。
4. **貼り付けられた指摘の 3 点**。利用者が貼った文章は「差が出るのは主に次の3点です。-」で切れていて、3 点の中身が届いていない。04 の棚卸しはコードから作った。抜けがあれば 04 の表に足す。
